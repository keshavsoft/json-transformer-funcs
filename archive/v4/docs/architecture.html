Architecture guide · src/v12

Compose a table as data

The architecture separates table content, repeated tag shapes, and the table's outer structure. A builder combines them into a JSON tag tree. A renderer can then turn that description into browser DOM.

Datacolumns + row records
Templatesreusable tag descriptions
Builderclone, fill, and place
JSON treeinspectable output
Rendereroptional DOM step

Two composition paths

The public API is the direct route for a conventional header and body. The samples show how to compose additional pieces such as colgroups and footers.

Direct API: tableFromData

Reads inData.columns and inData.rows, uses header and body templates, clones the scaffold, and fills the first header row plus the body. This is the normal public entry point.

columns + rows + spec + scaffold → tableFromData → JSON tree

Stepwise composition: collection helpers

Calls helpers for the desired repeated parts and assigns each result into a scaffold path. The sample JavaScript interprets instruction records to select the inputs, helper, and destination.

source key + template key + helper + path → one table part
instuctions.json belongs to the sample composition pattern; tableFromData does not load or interpret that file. The sample's index.js implements the small instruction loop.

The table model

The scaffold defines the stable places in the output. The data and templates provide arrays of nodes to insert at those places.

Scaffold child slots in the full sample

table.children[0] → colgroup
table.children[1] → thead → first tr
table.children[2] → tbody
table.children[3] → tfoot → first tr

The default v12 scaffold is smaller: it has a thead and a tbody. Custom structures need to provide the nodes required by the operation being used.

What each input owns

  • Data owns values and their order.
  • Templates own tags, attributes, text, and nested children.
  • The scaffold owns outer table structure and styling.
  • The builder owns cloning and insertion.
  • The renderer owns DOM creation and mounting.

Instruction records are routing metadata

An instruction connects the pieces by naming them. The JSON record stays declarative; the registered JavaScript helper does the work.

{
  "sourceKey": "columns",
  "templateKey": "buildHeader",
  "func": "collectionFromKey",
  "destinationPath": [
    "children", 1, "children", 0, "children"
  ]
}

Resolve: read inData[sourceKey] and sampleSpec[templateKey].

Build: look up func in a local registry and call it with the chosen source and template.

Place: walk destinationPath on a cloned scaffold and replace the target child array with the generated nodes.

table.children[1].children[0].children → header cells 
const input = {
  source: inData[instruction.sourceKey],
  template: sampleSpec[instruction.templateKey]
};
const nodes = functionRegistry[instruction.func](input);
setByPath(table, instruction.destinationPath, nodes);

What the v12 helpers do

collectionFromKey

Maps a template over an array. For each item, it clones the template and applies placeholders using that item as the context. It suits headers, columns, controls, and other one-item-to-one-node collections.

collectionFromInternal

Maps records to outer nodes, then maps each record's Object.values to inner nodes. The row value order must match the intended cell order; it does not look up values by column name.

Template application

Templates are cloned with structuredClone. Placeholder strings are replaced recursively in string values, text, attributes, and children. Current token names match \w+; missing properties leave the token unchanged.

Renderer boundary

The package returns ordinary JSON-compatible data. It does not know about document, events, mounting, or browser state. A separate renderer such as json-to-tag consumes the tree.

How the current samples explore the architecture

There are four top-level v12 cases. The nested html/footer folder is a subcase of the browser integration example.

CaseArchitectural ideaCurrent fixture behavior
columnsReuse column contexts for widths, header cells, and footer controls.Header and footer paths omit the row index and do not populate the intended cell arrays.
rowsMap a data collection into repeated output nodes.Uses a bare tr template; the generated rows contain no cells.
rows_goodAddress colgroup, header, body, and footer independently in one scaffold.Paths address the intended slots, but its body instruction still selects the bare tr template; buildBody1 is defined but unused.
htmlPass a generated tree across the renderer boundary.The nested footer builder fills header/footer. The browser entry does not use colgroup/body instructions; the large batches.json file is not imported there.
The examples illustrate composition ideas, but they are not all complete implementations. The live user guide shows a complete header/body result from the public API.

Source map and design limits

→ tableFromData

Contracts to keep visible

  • The body helper uses row property enumeration order.
  • The default table fills header and body, not colgroup or footer.
  • collectionFromArray is exported but currently returns undefined.
  • The transformer builds a JSON description; rendering remains a separate step.
